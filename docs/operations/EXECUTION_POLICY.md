# 障害対応・部分継続の実行方針

executionPolicyVersion: `1.0.0`
入口は[CURRENT.md](CURRENT.md)。機械設定は[operations-policy.json](../../config/operations-policy.json)。
保管・削除・保護期限は[RETENTION.md](RETENTION.md)。公開・認定は[PHASE0.md](PHASE0.md)と[RELEASE.md](RELEASE.md)の承認境界を維持する。

## 常時適用と実装範囲

Codexはプロジェクト作業の開始時にAGENTS.mdからCURRENT.mdを読み、この方針のVersionと機械設定の一致を確認する。
Skillにこの手順を複製しない。文書と設定に不一致があれば、関連する工程をBLOCKEDにし、独立した工程を継続する。
この変更の正式main反映までは作業ブランチ上の実装であり、正式mainのルールを切り替えたとは扱わない。

今回実装するのは参照入口・規則・オフライン検証である。Codexのツール通信を強制中断する自動制御には接続していない。
公開プログラムにも接続しない。DESIGN_ONLY、Genesis未認定、新方式の公開不許可を維持する。

## 作業開始時に工程と予算を記録する

工程ごとにID、目的・証明範囲、依存工程（安全上の前提を含む）、状態、担当、正常時の時間予算を定める。
正常時の予算は正の秒数で指定し、開始日時と進捗確認時刻を記録する。長時間処理は短いyieldと進捗確認を使い、予算超過を黙って無制限に延長しない。
正常処理が遅いことと認証障害を混同しない。11分はタスク全体や正常処理の時間上限ではない。

障害が起きたらincident ID、サービス、認証・権限範囲、操作群、原因、開始日時、影響工程を記録する。
同じ認証・権限・操作群に起因する401/403は、Workerや言語が異なっても同じ障害として扱う。
ツール変更、タブ追加、対象言語追加、会話の再開・要約で予算や試行回数をリセットしない。
同じ障害を別IDに付け替えて上限を回避しない。初回試行後の再試行も含めて、根拠と使用時間を引き継ぐ。
接続拒否・タイムアウト・外部サービス障害にも同じ探索予算を使い、401/403専用の試行条件は認証障害に適用する。

## 閾値の正本

| 機械キー | 対象 | 上限 |
|---|---|---|
| initialDiagnosisMinutes | 初期診断 | 3分 |
| additionalDifferentCauseAttempts | 原因条件が異なる追加試行 | 2回 |
| alternativeRouteKinds | 正規の代替経路 | 2種類 |
| alternativeRoutesMinutes | 代替経路全体 | 5分 |
| redesignMinutes | 方法の再設計 | 3分 |
| incidentTotalMinutes | 障害1件の合計 | 11分 |
| maxBlockingCallSeconds | 同期的に待つ1回のツール呼出し | 60秒 |

時間は実時間で計測し、API待機・ブラウザーの読込・UI確認・同一障害の資料探索を含める。
診断3分・代替5分・再設計3分をそれぞれ上限とし、未使用時間を別段階へ移さない。
段階開始時に「段階の開始＋その上限」と「障害開始＋11分」の早い方を終了期限として記録する。
実行中は単調増加時計で経過を計測し、引き継ぎには絶対日時・使用時間・残予算を残す。計測不能なら関連探索をBLOCKEDにする。
ツールのtimeoutは段階・全体の残秒数と60秒の最小値以下にする。残りがなければ新しい呼出しを始めない。
上限またはユーザーの終了指示に達したら新規探索を終了する。進行中処理は対象と副作用を確認して安全に終了し、未完了を成功扱いしない。

## 401/403の初期診断

エラーの日時・HTTP status・秘密値を除いたerror code、必要な権限、認証の有効期限等を既存情報で確認する。
同じ条件の無意味な再試行は禁止。追加試行は最大2回で、各試行の前に異なる原因条件・その根拠・何を確認できるかを記録する。
URLの言語・Worker名やツールだけを変えても、認証条件が同じなら異なる原因の試行とは数えない。
明確な期限切れ・権限拒否なら診断を早期終了し、残りの試行枠を消化しない。
認証情報・token・Cookie・secret値を通常レポートへ出さない。エラー本文や画面内容も秘密値を除いて必要な部分だけ記録する。

## 正規の代替経路

元の承認範囲内で、既存の正規認証・権限を使える経路を選ぶ。最大2種類、全経路を合算して5分まで。
例は既存のログイン済み管理画面、既に承認された公式の読み取りAPI・export等。対象サービス・データ範囲・正当な権限・証明範囲を確認してから使う。
認証や権限を回避する未承認経路、他人のセッション、秘密値の抽出、無断の権限拡大は使わない。
別タブ、別Worker、別言語、同じ画面の反復は別経路とは扱わず、同じ5分の予算に含める。
公式手順でも書き込みや新たな承認が必要なら、自動実行せず必要なユーザー操作として記録する。
HTTP標本、UIの短縮ID、ローカルhash、fixtureが証明できる範囲を超えて認定に使わない。

## 方法の再設計と探索終了

通常経路と代替経路で必須情報を得られなければ、取得済み情報を使い最大3分で整理する。この段階で追加の外部探索をしない。
必須情報とその必要性、未確認の取得方法・代替案、独立して継続できる工程、必要なユーザー操作を区別して記録する。
上限後は同じ探索へ戻らない。取得不能・未実施をUNKNOWN／不足として残し、認定や成功を推測で補わない。
再開には解決条件が満たされた証拠を確認する。同じ障害が未解決なら残予算を引き継ぎ、予算を再発行しない。
予算を使い切った後の追加探索は、対象・新しい根拠・追加予算を明示した別のユーザー指示を必要とする。

## 工程状態と部分継続

| 状態 | 意味 |
|---|---|
| COMPLETED | 定めた工程の証明範囲で結果を確認済み |
| IN_PROGRESS | 必要な前提を満たし、正常予算内で処理中 |
| BLOCKED | 必須の前提・証拠・許可が不足し、関連処理を実行しない |
| NOT_STARTED | まだ開始していない。前提を満たす工程は次に開始できる |

BLOCKEDにはreason（理由）、resolutionCondition（客観的な解決条件）、decisionDeadline（時刻・タイムゾーン付き絶対期限）、owner（担当）、alternative（代替案。無い場合はその理由）を必須とする。
incident ID、影響工程、失敗した経路・使用時間、必要なユーザー操作も関連記録に残す。
判断期限は無期限にせず、作業枠・合意した再確認日時に基づいて定める。到達時は再判定・報告し、黙って延長・成功扱いしない。
BLOCKED工程とその依存工程は開始せず、独立した承認済み工程を継続する。依存のない文書整理・レビュー等まで一律に停止しない。
安全上の前提も依存として扱う。例としてPushがProductionを書き換えない確認に依存する場合、Pushを無条件に独立工程としない。
共有の前提不足で全実行工程が止まる場合は、取得済み情報の整理・部分結果報告を行い、必要な操作を提示して終了する。
工程のBLOCKEDは成果物の保護状態ではない。保管・期限・削除はRETENTION.mdに従い、BLOCKEDを無期限保護に使わない。

## 今回のGenesis調査への適用例

Cloudflareの401/403で明確な期限切れが確認できた時点で診断を早期終了する。
承認済みの既存Dashboard等を使う場合も5分の予算を6 Worker全体で共有し、同じ探索を言語ごとに反復しない。
完全なVersion／Deployment／資産集合が不足するならGenesis認定工程をBLOCKEDにし、台帳レビュー等の独立工程は継続する。
API認証をユーザー側で再確立する等の解決条件・判断期限・担当・代替案を記録する。UI表示やHTTP 200を完全資産の証明に代用しない。
完了・一部取得・未取得・次のユーザー操作を分けて報告する。今回のルール実装もGenesis認定や公開の許可にはならない。

## 限定検証

`node scripts/validate-execution-policy.mjs` でVersion・参照・設定閾値・DESIGN_ONLY等を読み取り検証する。
`node --test tests/execution-policy.test.mjs` で設定／文書の不整合、閾値改変、工程の依存・BLOCKED記録をオフライン検証する。
公開スクリプト、外部API、ブラウザー、削除、全サイトビルドには接続しない。合格をツールの自動中断や実Productionの認定成功と混同しない。
