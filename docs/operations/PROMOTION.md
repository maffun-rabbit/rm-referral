## 計測
Instagram・TikTok・Threads・はてな・Cloudflareを共通ルールで扱う。次回制作・更新から、読者向けコンテンツ内リンク（記事誘導、公式案内、紹介CTA）を短縮URL管理へ登録して本文または実際のリンク設置箇所へ設定する。出典台帳には元の公式URLを保持する。Cloudflareガイド・トピックスは記事別、ショップの基本粒度は都道府県×キャリア。言語も属性として保持する。
キーは媒体×記事slug（ショップは都道府県×キャリア）×行先/目的×設置箇所。異なる媒体・記事のURLを使い回さず、同じキーの既存登録は再利用する。記事への流入、公式案内、紹介キャンペーンへの送客を分ける。自サイトへの流入には対応するUTMも設定し、外部公式URLは不要なパラメータを足さない。
登録→短縮URLの遷移先照合→本文/リンク設置→限定確認を1工程とし、キー・短縮URL・元URL・設置箇所・公開状態を記録する。本文URLだけでタップ可能と扱わず、対象アカウントの実際の仕様を確認する。本文リンクが使えないSNSは投稿専用のプロフィール項目・ストーリーズ等を使い、本文の案内も一致させる。共通プロフィールのクリックを特定投稿の成果と断定しない。未公開記事のURLは登録可能だが、記事公開確認まで誘導投稿は保留する。
クリックは申込み・開通とは別の中間指標。確認アクセスの回数と時刻を記録し、集計の混入を明示する。既存全ページを一括変更しない。短縮URL登録はSNS投稿・プロフィール変更やCloudflare公開の承認を代替しない。

## SNS動画の標準尺
Instagram・TikTok向けのページ/スライド動画は、正式な標準尺を1ページあたり2秒とする。8ページなら16秒。枚数が変われば総尺はページ数×2秒。明示指定があればその指定を優先する。
画像をそのまま動画化する場合も各ページを2秒表示し、追加の末尾静止・トランジションで標準総尺を延ばさない。書き出し後に実ファイルの尺と各ページの表示時間を確認する。動画・個別の納品ファイル・制作記録の尺を一致させる。納品は個別ファイルとし、新しいZIPを作らない。32秒を標準にしない。

## 制作と公開の分離
主担当が進行・計測・生成・承認・公開を管理する。コンテンツ工程は公式情報リサーチ、検索意図と重複確認、構成・本文・出典・確認日・CTA意図を確定する。受け渡しは本文データ、locale/route、出典・確認日、CTA行先・計測キー、必要依存、媒体別原稿に絞る。
原則は1エージェントで工程を分ける。複数テーマや調査と実装の並行が有効なときだけ、利用可能なら限定したコンテンツ工程を別エージェントへ委任してよい。全履歴を渡すことや二重リサーチ・二重監査を標準にしない。公開書込みは主担当に集約する。別のユーザー所有チャットへのメッセージ送信許可とは区別する。

## 軽い公開処理
記事ごとにWorker・routeを新設しない。既存Workerを再利用し、変更ページと必要依存のみ生成・確認する。全サイトビルド・全件HTTP・全資産再コピーは通常制作で禁止。成功済み検証の再実施には変更・障害など具体的な理由が必要。
公開必須の確認は対象/差分/既存公開内容の保持と、Upload前・切替直前の正確な親Current照合。親が異なる、状態不明、未承認なら該当公開を止める。無関係な監査suiteは走らせず、共通コードの変更時は影響に対応する代表確認を行う。
CURRENT.mdのPhase 0 DESIGN_ONLY・Genesis制約をこの文書で解除しない。明示承認を受けた既存content-updates経路で実行する場合も、承認されたURL範囲とpackage/Versionを固定する。既存の旧公開CLIへこの簡略化を無条件に適用したり、そのガードを迂回しない。
任意URL公開は実現性確認済みだが未実装。現在のcontent-updates routeはreplacement-program配下のみ。対象外では最小構成変更を準備して承認を求める。実装済みと扱わない。
公開後は対象URLのHTTP 200・内容/CTA反映を限定確認。エラー時の診断はEXECUTION_POLICY.mdに従う。

## SNSライター・編集者の制作方針

テーマの調査・選定から文章、タイトル、CTA、カルーセル、キャプションまでを担う。画像生成方式や特定の商品・題材に依存しない。読者が「自分に関係がある」「判断に役立つ」「次に何をすればよいか分かる」と感じる内容をつくる。正確さ、読者への有用性、興味、信頼、行動のつながりを同時に設計する。

### 自律的なテーマ選定

依頼でテーマが指定されていれば、そのテーマを維持し、調査で切り口と対象読者を絞る。統合制作では確定済みの記事テーマ・記事との整合を優先する。未指定なら正式運用ルール、既存記事、制作物カタログを確認し、現在のWebリサーチを行ってテーマを選ぶ。旧Vaultや過去のサンプルをテーマの正本にしない。

調査は読者の疑問・迷い・判断の場面を見つけるために行う。公式FAQ、手続き案内、サービス変更情報などから使える事実を集め、必要に応じて公開された質問や体験談から読者の言葉を拾う。質問・体験談は関心の手がかりであり、制度や効果の根拠にはしない。検索結果の断片だけで結論を出さず、採用する情報の元ページと適用条件を確認する。

候補を複数、通常3件程度検討し、次の観点で比較する。数字の採点を埋めることより、採用理由を説明できることを重視する。

- 誰の、どの場面の問題を解くかが具体的か。
- 読者が知りたいこと、避けたい手間、重視する価値に応えられるか。
- 一次情報で裏付けられ、既存情報に対して新しさや別の有用な切り口があるか。
- 8枚・16秒で一つの理解や判断を届けられるか。
- 制作目的と合い、読後の行動と行先が用意できるか。

話題性だけで選ばない。需要データがなければ「検索が多い」「今話題」「みんな困っている」と断定しない。調査結果から最適な一件を自ら選び、候補と選定理由を原稿に短く残す。重要な前提が依頼から判断できない場合だけ確認し、日常的な企画判断をユーザーへ戻さない。調査できない場合は確認済み情報で扱える範囲へ絞り、制約を記録する。調査未実施を調査済みと扱わない。

### 読者と編集方針を決める

書く前に、次の項目を短い制作メモにする。人口属性だけでなく、読む瞬間を具体化する。読者心理は調査で分かった事実と書き手の仮説を区別し、固定観念で決めつけない。

- 読者の場面：今何をしようとしているか。何を知っているか。
- 最も気になる疑問：読者自身の言葉で一つ。
- 重視すること：費用、時間、手間、失敗の回避、使い心地など、今回の判断に関わる価値。
- 行動を妨げること：用語が分からない、条件が判断できない、面倒そうなど。
- この投稿の約束：読み終えると何が分かる・判断できるかを一文で。
- 主な次の行動：読者の準備段階に合う一つと、その行動をする価値。

同じテーマでも、検討中・手続き前・利用中・問題発生後では疑問と行動が異なる。8枚で複数の状況を扱うと混乱する場合は、対象を絞る。安心は結果の保証でなく、確認するもの、判断の手順、困ったときの進み方でつくる。

### 根拠と伝える順序

執筆に使う主張について、根拠URL、確認日、適用対象・条件、必要な行動、未確認事項を整理する。料金、特典、期限、制度、効果などは現在の一次情報で確認する。確認できない効果、体験談、数字、限定性を作らない。

説明側の分類順ではなく、読者の疑問が解ける順序を設計する。共感→解決のヒント→理由→次の一歩、比較軸→違い→選び方、状況→対象条件→対応、などから目的に合う流れを選ぶ。共感の段落や問いかけを全テーマに強制しない。

3つのヒントは内容を整理する選択肢とする。未指定なら調査と読者理解から考え、テーマ・ヒント・順序が指定されていれば尊重する。ただし誤りや誤解につながる順序なら理由を示して修正する。数を揃えるために薄いヒントを足したり、同じ意味を言い換えて水増ししたりしない。

### 約400字の文章を執筆する

まず一つの読み物として、冒頭から結びまで意味と流れが通る約400字の文章を書く。文字数は目安であり、条件を削ったり冗長な文章を足したりして一致させない。画像に収める作業はこの後に行う。

- 冒頭は、読者が自分との関係や読む価値を判断できる言葉にする。
- 抽象的なメリットを、確認済みの機能や手順が読者の生活・判断にどう役立つかへ翻訳する。
- 「不安ですよね」を置くだけで共感したと扱わない。迷う理由や負担に応える情報を示す。
- 専門語は必要なものを残し、初出で理解できる言葉を添える。説明のための専門語を増やさない。
- 「自己判断しない」などの禁止だけで終わらせず、代わりに何をすればよいかを示す。
- 親しみやすさは語尾の演出より、相手の負担を減らす具体性でつくる。責める、決めつける、過度に馴れ馴れしい表現を避ける。
- 恐怖、誇張、虚偽の希少性、架空の体験、根拠のない保証で興味を引かない。広告・紹介であることを隠して信頼を得ようとしない。

### タイトルを選ぶ

文章から、悩みへの理解、解決のヒント、続きを知る価値が最も伝わる核を取り出す。方向の異なるタイトル候補を通常2〜3案考え、原則15文字前後に整える。短さより、内容との一致と読者が自分に関係すると判断できることを優先する。

- **見せるタイトル**：答えや読む価値を示す。判断・手続き・重要なお知らせなど、理解の速さが必要な場合に向く。
- **隠すタイトル**：理由や意外な点を問いにする。答えを本文で早めに回収でき、隠しても誤解しない場合に使う。
- **キーワード**：制度名・商品名が対象の識別や理解に必要なら含める。読者の日常語が届きやすい場合はタイトルから外せるが、本文の早い段階で対象を明示する。

必須条件や危険に関わる情報を、好奇心のために隠さない。「絶対」「完全」「誰でも」など本文で保証できない約束をしない。選定した案と選定理由を原稿に残す。

### CTAを設計する

申し込み、条件確認、記事閲覧、保存、比較、問い合わせなどから、投稿の約束と読者の準備段階に合う主な行動を一つ選ぶ。理解や確認が必要な読者へ、いきなり申し込みを求めない。テーマがトラブル対応なら、販促CTAより問題解決を優先する。

CTAは「何をするか」「それで何が分かる・役立つか」を具体的にし、柔らかくても曖昧にしない。「詳しくはこちら」だけで終わらせない。保存は後で参照する価値がある内容に使い、次の投稿への誘導は実際に続きが用意される場合に使う。

8枚目を主なCTAとし、キャプションも同じ行動にそろえる。複数の行先を並べて選択を読者へ押し戻さない。制度説明に必要な出典の掲載は別に保持する。設置先、行先の公開状況、媒体別の計測URLはこのファイルの計測・媒体アカウントの節で確認する。架空のアカウント、ハイライト、リンクを作らず、未設置の導線を利用可能と書かない。素材制作の依頼だけでプロフィール変更・投稿を行わない。

### 8枚のカルーセルへ再構成する

1枚目にタイトル、8枚目にCTAを置き、2〜7枚目を読者の理解が進む順序にする。400字の文章を機械的に等分せず、文章の核を短い文言へ書き直す。

3つのヒントに各2枚を使う場合は、前半・後半の役割を変える。「疑問→答え」「選択肢→選ぶ条件」「必要なもの→使う場面」など、一枚目を読むと次の一枚に進む意味がある関係にする。手順・比較・お知らせでは配分を変えてよい。

1枚1メッセージ、基本2行。一枚43文字以内は上限であり目標ではない。実際の2秒表示では、文字数だけでなく、専門語、数字、条件の多さも含めて読み切れる量へ減らす。

対象条件や例外をキャプションだけに移すことで、画像が無条件の断定にならないようにする。重要な条件と結論を別画面へ分けて誤解を生む場合は、切り口を狭めるか、動画の役割を確認のきっかけに変える。問いかけを使ったら本文で答え、答えを伏せたままリンクだけへ送らない。

### キャプションをつくる

冒頭は表示範囲が媒体・環境で変わっても読む価値が早く分かる短文にする。「1行目は必ず省略されない」と仮定しない。次の型からテーマに合うものを選び、型を使うこと自体を目的にしない。

1. **タイトル・要点**：【 】などで対象や読む価値を示す。装飾や「完全保存版」を自動で付けない。
2. **疑問・意外性**：読者の疑問や根拠のある意外な点から始め、本文で回収する。
3. **お知らせ・メリット**：事実として確認した変更、特典、利用価値を読者の立場で伝える。「限定」「残り○名」は確認できた場合だけ使う。
4. **アカウント・入口**：実在するアカウントと設置済みの項目を具体的に示す。媒体ごとの利用可能な入口に合わせる。

本文は、400字の文章を活用する、画像で省いた条件・背景・具体例を補う、短い補足で終える、の中から選ぶ。画像の文言を繰り返すだけにしない。必要な条件・出典・広告表示があるときは、挨拶だけの短文にしない。体験やストーリーを書く場合も、本人の実体験を創作しない。

改行は意味のまとまりを優先する。15字前後の短い行や2〜3行ごとの段落分けは目安とし、助詞・固有名詞・URLを途中で切らない。空行を機械的に2行ずつ挿入しない。Instagram・TikTokのキャプションは主張とCTAをそろえ、誘導文と改行は各媒体に合わせる。

### 編集してから画像制作へ渡す

初稿を書いた後、編集者の視点に切り替えて次を確認する。見つけた問題は文言だけでなく、必要なら対象読者・構成へ戻って直す。

- **読者理解**：誰のどんな瞬間に役立つか。心理の決めつけや、本人が知らない専門語を前提にしていないか。
- **興味と約束**：冒頭に読む理由があり、タイトルの約束を本文で果たしているか。
- **有用性**：一般論や項目名の羅列に終わらず、読者が判断・行動できる情報があるか。各枚が理解を進めているか。
- **信頼と安心**：根拠と条件があり、煽りや保証に頼らず確認手順で迷いを減らしているか。
- **行動**：主な次の一歩が一つで、何を得られるかと実際の入口が一致しているか。
- **短文化**：約400字の文章、画像、キャプションの間で対象条件・数値・義務の強さが変わっていないか。
- **視聴**：8枚を2秒ずつ進む想定で、読めて意味がつながるか。写真が伝える場面と文言が一致しているか。

事実の誤り、条件欠落、約束の未回収、使えない導線は必ず修正する。流暢さや興味の強さで相殺しない。根拠不足は追加調査、関係の薄さは読者・テーマの絞り直し、読みにくさは語順・情報量・配分の見直しで解決する。

制作メモには候補と採用理由、読者の場面・疑問・重視すること、投稿の約束、採用タイトルの理由、CTAと行先、重要な根拠・未確認事項、主要な編集修正を簡潔に残す。詳細な思考過程や採点表は納品しない。文章QAを通った確定文言と写真の場面を画像制作へ渡し、生成後も意味・条件・原稿一致を確認する。


## SNS制作実務

原稿確定まではライター・編集工程、確定後は主担当の画像・動画・計測工程とする。既存原稿を受け取った場合も今回の正本の文章QAで必要な修正を判断する。別エージェントは必須ではなく、前述の限定委任条件で使う場合は本文・根拠・条件・CTA目的を渡し、主担当が媒体別短縮URLと正式@名を設定してから制作する。

### 保存先

実行中のローカル制作ワークスペースの `outputs/<制作案件>/YYYYMMDD/`（既存なら `YYYYMMDD_2/`、`YYYYMMDD_3/`）。Google Drive同期フォルダ・Obsidianを保存先にしない。

- `YYYYMMDD` は投稿対象日。指定がなければ実行日を使う。
- ディレクトリがなければ作成する。
- 同名ファイルを上書きしない。既存フォルダ/ファイルがある場合は `_2`、`_3` の順に枝番を付ける。
- 納品はこの日付フォルダへ個別ファイルを保存する。ZIP化・アーカイブ化・ZIPのアップロードや納品リンクの作成は行わない。既にZIPで作成された成果物は新しい正式納品物と区別する。ユーザーの別途削除承認なしにZIPや旧フォルダを削除しない。
- テーマ名は内容が分かる日本語名を基本とし、`/`、改行、制御文字などファイル名に使えない文字を除去する。
- Vault内には生成したPNG、MP4、背景画像、JSON、HTMLなどの実体を保存しない。
- 完成後は 正式リポジトリの `docs/promotion/SNS_CATALOG.md` へ、制作日、テーマ、対象媒体、成果物、実体フォルダ、公開状況を追記する。

### 原稿

Markdownを `{通番}_{テーマ名}.md` として保存する。本文には次を含める。

- 制作メモ：調査したテーマ候補と採用理由（未指定時）、読者の場面・疑問・重視すること・障壁、投稿の約束、構成意図
- タイトル候補、採用タイトル（原則15文字前後）と選定意図
- 約400字の投稿原稿
- 8枚分のカルーセルテキスト
- 主な次の行動を一つに絞ったCTAと、行動する価値・実際の入口
- Instagram用キャプションと必要十分なハッシュタグ（Instagramを対象にする場合）
- TikTok用キャプション（TikTokを対象にする場合）
- 調査・参照した情報のURLと確認日、重要な対象条件、未確認事項（主張の根拠は一次情報）
- 文章QAで行った主要な修正の要約

画像へ流し込む文言は、確定した8枚分のテキストと完全に一致させる。料金、特典、条件、期限など変わりうる情報は、生成時点の公式一次情報で確認する。推測で補わない。広告・紹介であることの表示が必要な場合は投稿キャプションに明示し、画像から削除したことを理由に表示自体を省略しない。

### 静止画生成

InstagramとTikTokの画角は同じ（9:16、1080×1920）のため、静止画はサービス別（Insta/TikTok）に分けず、カルーセル画像として**8枚（1セット）**を出力すればOKとする。

ユーザーが写真・文字・余白を一体で設計する一枚画像方式を希望した場合、imagegenスキルを読み、全体構図を設計して生成する。テーマに合う場面、短い確定文言、大きな文字、十分なコントラストを指示する。生成後に日本語の誤字・条件・読みやすさを目視確認し、誤りがあれば修正してから動画化する。完成画像を一体化してよいが、確定原稿と生成指示を保存する。この方式では下記の背景だけ生成・別レイヤー保持の規定は適用しない。

方式が未指定の場合、従来の写真背景・半透明パネル・太字を標準として、次の順で生成方式を選ぶ。

1. 既存の正本Figmaテンプレートのfile/nodeが特定でき、Figma MCPの呼び出し上限と編集権限に問題がなければFigma方式を使う。Figma操作前に このファイルの「Figma MCP生成ルール」節 と `figma-use` スキルを全文読む。
2. Figma MCPが未接続、正本テンプレート未特定、権限不足、利用上限、障害などで使えない場合は、確認待ちで止めずローカルHTML方式へ切り替える。実行前に このファイルの「ローカルHTML描画」節 を全文読み、`../../.agents/skills/sns-generator/scripts/render_carousel.py` を使う。

一度選んだ生成処理の途中で方式を混在させない。完了報告で使用した方式を明記する。

テンプレート:

- 出力: 9:16、1080×1920 PNG、8枚（1セット）
- 背景は写真を使用し、生成前に次のどちらかを選べるようにする。
  - AI生成: テーマに合う縦長写真を生成して使用する。
  - ユーザー提供: ユーザーが指定・添付した写真を使用する。
- 本人指定のAI生成写真を通常の選択とし、テーマに合う場面を設計する。提供写真の指定があればそちらを優先し、案件内で確認済みの選択を聞き直さない。
- 写真には文字、ロゴ、透かし、UI、広告表現を含めない。主題は中央の文字領域と競合しない位置へ置く。
- 1枚の写真を8枚で共用しても、8枚別々の写真を使ってもよい。指定がなければ統一感を優先して1枚を共用する。
- 写真の上に既定の半透明パネルと文字を別レイヤーで重ね、写真へ文字を焼き込まない。

Figma方式では正本テンプレートを直接上書きしない。対象ノードを複製した作業用フレームへテキストを反映し、元ノードを保持する。既存テンプレートの意図的な背景や装飾は維持するが、ユーザーが指定していないテキスト背景、帯、カード、バッジ、注釈、装飾コンテナを新設しない。

Figma方式では、テンプレートの `opacity`、各Paintの `opacity`、ブレンドモード、エフェクトを保持し、PNGをFigmaノードからネイティブに書き出す。ローカルHTML方式では、付属テンプレートの半透明度を変更せず、Chromeのネイティブページキャプチャで書き出す。

AI生成を選んだ場合は、`imagegen` スキルを全文読んで背景写真だけを生成し、出力フォルダへ保存する。ユーザー提供を選んだ場合は、指定画像を改変せず背景として読み込む。トリミングが必要な場合は中央基準の `cover` を基本とし、主要被写体が欠ける場合だけ位置を調整する。

ファイル名:

- サービス名（insta, tiktok）は含めず、`{1〜8}_{YYYYMMDD}.png`（または枝番付き `{1〜8}_{YYYYMMDD}_{枝番}.png`）とする。

### 画像品質

- 8枚分の確定原稿以外の注釈やサブタイトルを勝手に追加しない。
- 1枚1メッセージ、基本2行の短文、各枚43文字以内とする。上限まで埋めず、2秒で読み取れる量を優先する。詳細・出典は原稿とキャプションで補うが、対象条件や例外を移して画像が無条件の断定にならないようにする。短文化しても必要条件や義務の強さを変えない。
- 写真はテーマに合う場面、大きな文字と十分なコントラスト、自然な改行を一体で確認し、読み量を減らしながら意図が届く構成にする。
- 「1/8」などの番号バッジを追加しない。
- SNSでは短時間で読まれる前提に立ち、収まる範囲で最大のフォントサイズを使う。小さい文字で広い余白を残さない。
- ローカルHTML方式の標準文字サイズは108pxとし、収まらない場合だけ段階的に縮小する。
- 改行は助詞や語句の途中を避け、意味のまとまりで2〜4行にする。日本語は1行およそ8〜12文字を目安とし、1文字だけ次行へ落とさない。
- フォントは太字を基本とし、行間を詰めすぎず広げすぎない。文字サイズ、行間、太さ、配色、余白を8枚通して統一する。
- フォントサイズ、行間、幅を調整し、文字をフレーム外へはみ出させない。自動縮小へ頼る前に自然な改行を設計する。
- 文字と背景のコントラストを確認する。視認性が不足しても、未指定の背景帯を追加せず、まず文字色・配置・サイズ・写真の選択またはトリミングで解決する。
- Figma/HTML方式では写真と文字を独立レイヤーとして残す。一枚画像方式では一体化できる。

## Figma MCP生成ルール

Figmaでデザインを生成・編集するときは、見た目だけでなく、ユーザーが後から編集できる意味的なレイヤー構造を実装する。

### ノードの原則

- 文字は必ずネイティブ `TEXT` ノードにする。
- 写真はImage Fillを持つ適切なShapeまたはFrameとして保持する。
- 背景は視覚的に必要な場合だけFrameまたはRectangleにする。
- 区切り線はLINEまたは細いRectangleを使う。
- グルーピングと配置にはFrameまたはGroupを使い、複数要素のレイアウトはAuto Layoutを優先する。
- 見た目合わせやサイズ合わせだけのRectangle、Frame、透明Shapeを作らない。
- 写真と文字を一枚の画像へFlattenしない。

レイヤーは意味に応じて `Hero`、`HeroImage`、`HeroHeading`、`Description`、`CTA`、`SectionTitle`、`BodyText`、`Caption` などと命名する。`Rectangle 123`、`Frame 58` のような自動名を可能な限り残さない。

### TEXTの絶対ルール

`TEXT.fills` は文字（glyph）の色であり、テキストボックスの背景色ではない。

- 「文字を白に」: `TEXT fills = #FFFFFF`
- 「背景を白に」: 必要な背景FrameまたはRectangleのFillを白にする。
- CSSの `color` はTEXT fillに相当する。`background-color` と混同しない。

テキスト周囲は透明をデフォルトとする。写真上に白文字を置く場合は、白い箱を作らず、写真の上へ白いTEXTノードを直接配置する。

```text
HeroFrame
├── Photo
├── Heading       TEXT / fill #FFFFFF
├── SubHeading    TEXT
└── Caption       TEXT
```

文字間、行間、TextNodeの余白から背後の写真が見える状態を保つ。

### 背景を作らない

ユーザーが明示しない限り、次を作らない。

- Textの背後のRectangle
- Fill付きTextContainerまたはFrame
- 半透明の黒帯、白背景、ハイライト
- カード、ラベル、バッジ、ボタン、パネル
- 「画像上の文字」という理由だけのOverlayやグラデーション
- テキスト領域いっぱいの塗り
- 文字色を表現するためのRectangle

背景を生成できるのは、「背景を付けて」「黒い帯」「半透明の帯」「ラベル」「バッジ」「カード」「ボタン」「ボックス」「パネル」「テキスト背景」「文字の後ろを黒く」「グラデーションを敷いて」など、ユーザーが明示した場合だけとする。判断に迷う場合は背景を作らない。

### FrameとAuto Layout

配置、グルーピング、Padding、Alignment、ResizeのためだけのFrameは、`Fill: none` をデフォルトとする。複数テキストは必要に応じ、透明なAuto Layout Frameへまとめてよい。

```text
TextGroup          Auto Layout: Vertical / Fill: none
├── Heading        TEXT
├── Description    TEXT
└── Caption        TEXT
```

既存テンプレートに意図的なFillや背景がある場合は、それを「自動生成された不要物」と誤認して削除しない。このルールは、新規生成または指示対象の編集で余計な背景を追加しないためのものとする。

### 透過・書き出し

Figmaの透過は、主にノード全体の `opacity` と、`fills` 内の各Paintが持つ `opacity` の二段階に存在する。テンプレートを複製・編集するときは両方を保持する。

- Paintを変更する場合は既存Paintを複製し、未変更の `opacity`、`blendMode`、画像設定を残して再代入する。
- 半透明の白いPaintを、同じRGB値の不透明な白いPaintへ置換しない。
- ノード全体の `opacity` を既定値の `1` に戻さない。
- 既存のブレンドモード、背景ぼかし、エフェクトを、明示的な指示なしに削除しない。
- 文字差し替えだけの作業では、TEXT以外のノード属性を変更しない。

最終PNGはFigmaの対象ノードからネイティブにエクスポートする。HTML/CSS、Canvas、Playwrightのスクリーンショット、Pillowなどでデザインを再構築して書き出さない。これらはFigmaのPaint opacity、ブレンド、背景ぼかしを同じ意味で再現できない可能性がある。

エクスポート後は、Figma上の対象フレームのプレビューとPNGを目視比較する。背景写真を含む完成画像はPNG全体のアルファ値が255でも正常な場合があるため、ファイルのアルファチャンネル有無だけで半透明レイヤーの維持を判定しない。中央パネルなど、本来半透明の領域から背後の写真が同程度に見えているかを確認する。

### 生成前の判断

各ノードを作る前に確認する。

1. このRectangleは本当に必要か。
2. このFrameにFillは必要か。
3. ユーザーはテキスト背景を明示したか。
4. 文字色と背景色を混同していないか。
5. ネイティブTEXTだけで表現できないか。

必要性を説明できないノードやFillは作らない。

### 生成後の構造検査

Figma操作を完了する前に確認し、不適合があれば修正する。

- すべての文字が編集可能なTEXTノードである。
- 文字色がTEXTのFillに設定されている。
- 未指定のText背景Rectangleがない。
- Textを囲うレイアウトFrameに不要なFillがない。
- 写真が文字間とテキスト周囲から見える。
- 写真と文字が独立レイヤーである。
- 不要なRectangle、Shape、装飾コンテナがない。
- 各レイヤーが意味のある名前になっている。
- 元テンプレートと作業ノードで、ノードopacity、Paint opacity、blendMode、effectsが意図せず変化していない。
- ネイティブ書き出しPNGで、半透明部分が不透明な白または黒になっていない。

迷った場合は、ネイティブノード、少ないレイヤー、透明なレイアウトFrame、編集可能な構造を優先し、背景・Shape・装飾コンテナ・Fillを発明しない。
